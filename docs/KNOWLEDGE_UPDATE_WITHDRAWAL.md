# 知识页更新的安全撤回

本文说明 Web 中一次已应用 AI 知识页更新的局部撤回合同。实现允许用户对照历史、保留后续独立编辑，并明确处理冲突；完整 M0、真实跨设备并发与云端模型流程仍未验收。更新建议的生成、接受和本机审核草稿见 [资料整理](ORGANIZATION.md)，通用导出和恢复见 [导出格式](EXPORT_FORMAT.md) 与 [备份恢复](BACKUP_RESTORE.md)。

## 使用流程

打开知识页的“更新建议”，在有已应用建议的任务中点击“预览撤回”。预览不会修改正文，也不调用模型。

每项展示三个状态：

| 状态        | 来自哪里                                 | 用途                             |
| ----------- | ---------------------------------------- | -------------------------------- |
| 更新前 B    | 生成建议时保存的原始目标快照             | 核对被替换、移除或插入的原始位置 |
| AI 更新后 A | 本次任务实际接受的纯文本与累计应用后快照 | 区分真正采用的修改与未应用建议   |
| 当前内容 C  | 当前知识页和完整历史                     | 核对后来发生的人工编辑和位置变化 |

“可安全恢复”只表示系统能够证明当前位置唯一且局部逆向修改与后续编辑不重叠。界面默认选择恢复，用户仍可改为保留当前内容或手工合并。领域接口省略安全项时也默认恢复；冲突项必须明确处理。

“需要选择”的项没有自动恢复默认值。用户可以选择：

- **恢复更新前的内容：** 对能安全恢复的指定局部候选执行恢复；发生重叠时应核对将被恢复的内容。
- **保留当前内容：** 该项不修改正文，仍作为本次任务已处理的一部分封存。
- **手工合并：** 先明确当前局部位置，再输入最终纯文本。仅替换这个位置，文字中的 HTML 不会作为可执行结构写入；原富文本格式可能转为普通段落。

多个重复候选必须先选定位置，不能按第一次出现的文字自动推断。无法确认结构或定位的候选会禁用直接恢复，保留手工合并与保留入口。多个已选局部范围互相重叠时，整次提交拒绝；可把重叠部分合并为一个人工修改，其余项选择保留后重新核对。

候选只是需要用户核对的位置，不证明其中内容必然来自原 AI 更新。跨区移动或删除后重新复制的同文需要明确选择。较大差异无法定位时最多展示 24 个局部位置，界面明确提示此上限；其他位置可通过“返回知识页手工编辑”处理，之后重新打开撤回预览。

确认前必须处理全部冲突项。取消只关闭临时预览，不改正文；确认后仅修改本次选定的局部范围。

## 人工内容与引用保护

系统从原始快照、实际应用记录重建 A，必须与已保存应用后快照一致。它处理真正应用的修改组合，不把其他待审核建议当作已写入内容；多次接受同一任务的不同部分仍按累计应用记录核对。

能证明互不重叠时，后续独立段落、同段落的独立句子及明确的边界插入保留。位置移动、重复内容、结构变化和较大的差异可能无法证明安全，此时必须人工选择；不能承诺任意富文本编辑都能自动合并，也不提供整页覆盖作为兜底。

撤回保留当前标题、草稿／接受状态、所属知识库、AI 来源标记和 `manualExcerptRefs`。当前引用数组的顺序不变，不为撤回删除或重新排列当前引用；恢复所需但当前缺少的历史引用按原身份追加到末尾。恢复片段的可见编号按引用身份映射到当前数组，HTML 属性中的数字不作为正文引用标记改写。例如原引用顺序是 A，而当前顺序为 B、A、C，恢复的原 `[1]` 应指向当前的 A，即 `[2]`，已有 B、C 的编号和其他正文保留。

手工合并不会生成新的来源引用或自动判定输入的引用编号正确。用户输入的标记作为纯文本保存，应在知识页自行核对对应资料、版本和原话。

这是一项人工数据操作，不消耗模型次数。关闭全局 AI、撤销资料 AI 权限或来源不再适用于新生成，不单独阻止撤回已有记录。失效历史引用可以保留，不能据此宣称来源仍有效或观点已被证实；来源彻底删除导致任务记录或快照已清理时，也无法从不存在的任务撤回。

以下情况拒绝操作：任务没有已应用项或已封存；原始目标与请求身份不一致；原始建议、累计应用记录或快照无法相互核对；目标知识页已删除、当前版本低于应用后版本，或当前知识库不存在。历史记录不一致时，不把用户当前页当作新的原始基线。

## 新版本与任务封存

每次成功确认都保存撤回前的完整当前版本，继续增加正文 revision。不会删除原始应用前版本或把 revision 倒退为历史值。每页沿用最多 **30 个历史版本** 的规则；新增超出时，最旧历史按现有规则移出，不提供无限或永久历史保留。

即使所有项都选择保留，正文和引用完全相同，也必须保存当前版本、增加 revision 并记录本次确认。这意味着用户结束本次更新的审核，而不是暂时关闭面板。

成功后的 `organizationJobs[].updateReview.withdrawal` 封存整个任务：

- 不能再次撤回同一任务。
- 不能继续接受或忽略该任务未应用的剩余建议。
- 原始建议和应用后历史快照仍可查看；恢复某个笔记历史版本也不会解封任务。
- 继续修改应直接编辑当前页，或基于当前页重新生成新任务。

当前实现保留原 `updateReview.note` 作为历史应用后快照，receipt 的 `noteRevision` 指向撤回新版本，两者不同。收起或清理终态整理记录不撤销正文版本，但清理后无法再查看对应任务历史，建议按需先备份。

## 准备、提交与保存确认

领域接口位于 [knowledge-update-withdrawal.ts](../apps/web/src/lib/knowledge-update-withdrawal.ts)：

| 接口                                                                     | 行为                                                                                    |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `previewKnowledgeUpdateWithdrawal(data, jobId)`                          | 返回异步预览、局部候选、安全／冲突数量与 SHA-256 指纹；不修改工作区                     |
| `prepareKnowledgeUpdateWithdrawal(data, jobId, fingerprint, selections)` | 重新验证预览上下文、选择、结构和完整保存容量，返回冻结的临时准备对象                    |
| `commitKnowledgeUpdateWithdrawal(current, prepared)`                     | 在最新工作区同步核对完整 canonical 上下文，生成一次原子更新；对象必须由本次领域准备产生 |
| `withdrawKnowledgeUpdate(data, jobId, fingerprint, selections)`          | 准备后同步提交的便利接口；返回内存中的新工作区，自身不确认 IndexedDB 或云端保存         |

SHA-256 指纹绑定完整当前知识页，包括所有保留历史和手工摘录引用、完整任务请求／结果／审核记录，以及当前和原任务知识库上下文。准备对象还保留完整 canonical 比较值，以便同步提交核对；指纹不是独立授权令牌。准备后正文、引用、标题、状态、历史、任务或相关知识库内容改变，都必须重新预览。全局 AI 开关和来源生成权限不作为这项手工撤回的生成闸门。

准备对象只在当前运行时有效，不能手工构造、序列化后恢复或从备份重用。异步准备阶段之后，提交必须在最新工作区 reducer 中重新比较 canonical 内容，避免准备期间的编辑被旧撤回覆盖。

工作台通过 [persistKnowledgeUpdateWithdrawal](../apps/web/src/lib/knowledge-update-withdrawal-operation.ts) 捕获账号、操作 token、缓存模式与目标页；准备前、等待后、最新 reducer 内及保存返回时都复核上下文。切换账号、A→B→A 后操作 token 改变、目标页变化、页面卸载、账号封锁或进入不可写的恢复／冲突状态时，不把旧操作确认为当前页成功。

`updateDurably` 会先发布内存更新，然后等待该次工作区及同步元数据写入当前浏览器 IndexedDB。只有等待成功，界面才提示“撤回已保存到此浏览器”。写入失败时，修改可能仍保留在页面内存，必须查看错误、重试本机保存或导出后再离开；不能因为看到正文或 receipt 就认定最新修改可在刷新后恢复。

云端保存仍异步执行，以顶部同步状态、冲突和重试流程为准。本机成功不是 Supabase 已确认，也不能代替跨设备并发验收。结构、重叠、身份或容量检查失败时不提交部分局部修改；存储错误则按现有本机重试与恢复边界处理。

## 容量与算法边界

一次任务最多 12 项更新，手工合并每项最多 6000 字符。输入按纯文本与换行写成安全段落；不能通过输入标签保留表格、列表或富文本结构。局部差异比较有界，无法证明定位和结构时降级为明确的局部人工处理，不无限计算或静默覆盖整页。

正文、切块、笔记、全部保留历史、整理结果和 receipt 共用 **3 MiB** 工作区快照上限。准备阶段和最新同步提交均检查完整结果的紧凑 JSON UTF-8 字节数，超限拒绝，不截断正文或为此次操作额外批量清空其他历史。数据库另按最终 JSONB 文本复核，体积可能略大；本机检查通过不保证云端保存一定通过。

## Receipt 与备份合同

持久 receipt 只接受以下字段：

| 字段                | 含义                                            |
| ------------------- | ----------------------------------------------- |
| `id`                | 本次撤回确认的独立 ID                           |
| `at`                | 确认时间                                        |
| `noteRevision`      | 撤回新版本号，必须大于历史应用后快照版本        |
| `fingerprint`       | 64 位小写十六进制 SHA-256，表示已核对的原上下文 |
| `restoredChangeIds` | 恢复或手工合并的已应用变更 ID                   |
| `keptChangeIds`     | 保留当前内容的已应用变更 ID                     |

两组变更 ID 必须无重复、互不重叠，并完整分区本次累计已应用的 ID。未应用建议不加入该分区，但任务封存也禁止再次采用它们。空应用、未知 ID、分区缺项或多项、非法指纹／时间／revision，以及多余正文字段会被严格 schema 拒绝；没有 receipt 的旧审核记录仍兼容。

Receipt 不保存新正文或凭据。原任务已有的建议与审核快照继续保存，新增正文版本通过现有笔记历史保存。含正文的预览、候选、准备对象和 canonical 值只驻留内存，不写入本机审核草稿、不参与检索、云同步或 ZIP；已提交 receipt 随普通工作区快照进入本机存储、云同步及 `workspace.json`。

全库或单知识库导出保留完整任务及已选知识页历史；导出范围仅收集引用依赖，不重新排列正文编号。恢复 ZIP 为新增副本时，任务、页面、receipt 和两组变更 ID 一致重映射，历史版本号、时间和指纹保留。此时旧指纹只是原撤回的历史证据，不能验证恢复副本的新 UUID 或当前 canonical 内容；恢复的 receipt 仍封存任务，必须新建任务才能继续生成或应用更新。

## 部署与验收状态

本次撤回沿用普通工作区保存和笔记只读投影，没有新增专用云端撤回 RPC 或 SQL 迁移。仓库当前本地迁移链共 24 份；连接的 PRODUCTION 仍是已应用并核验 **19 份**，后 **5 份仅本地准备、未应用**，以 [云端配置](CLOUD_SETUP.md) 为准。本次本地实现不改变该状态。

真实云端撤回保存、双账号与完整跨设备并发、模型质量、processor 调度以及完整 M0 仍待各自验收。测试和页面核对记录统一写入 [开发状态](IMPLEMENTATION_STATUS.md)，本文不以本地实现宣称云端已部署或 M0 已完成。
