# 知识关系（KNO-04）

当前 Web 已实现两个知识页之间的类型化关系：可以手动建立，也可以对照原始资料请求 AI 建议，再逐项审核。关系独立保存，任何接受、编辑、删除或恢复操作都不会改写两页正文。

这是 KNO-04 的代码实现范围。真实模型与 Supabase 尚未联调，不能据此宣称关系判断准确或跨设备流程已经验收。当前没有 M2 的关系图谱可视化，关系也不进入问答检索。综合验证记录见 [开发状态](IMPLEMENTATION_STATUS.md)，资料整理及共同请求规则见 [资料整理](ORGANIZATION.md)。

## 类型与方向

在知识页工具栏打开“知识关系”，从同一知识库或收件箱选择另一份知识页。从任意一侧页面都能查看同一条关系。

| 类型           | 界面名称   | 含义与方向                                                     |
| -------------- | ---------- | -------------------------------------------------------------- |
| `synonym`      | 同义词候选 | 两页可能讨论同一概念，双向查看；不会自动合并页面或替换术语     |
| `related`      | 相关概念   | 两页之间存在待核对的关联，双向查看                             |
| `prerequisite` | 前置知识   | 起点是终点的前置知识，方向为起点 → 终点                        |
| `conflict`     | 冲突观点   | 两页中存在需要并列核对的不同观点，双向查看并保留各自条件与依据 |

同一对页面、同一类型最多保存一条未删除关系。除前置关系外，交换起点和终点视为同一关系；前置关系的两个方向分别计为不同记录。前置关系始终按记录中的起点 → 终点解释，从终点打开列表不会颠倒方向。

每条关系分别记录两侧观点、适用条件、原文引用，以及关系说明。观点与说明各最多 2000 字符，条件各最多 1000 字符，每侧最多 6 条引用，内容按纯文本处理。

冲突关系必须满足额外约束：两侧观点不能仅有空白差别；两侧都要填写条件，原文未说明时应如实标注；每侧至少有一个另一侧未使用的资料版本片段。两个独立片段可以来自同一资料。这些规则检查证据结构，不证明观点在语义上一定冲突，也不允许模型把不同立场合成没有依据的共识。

## 手动建立与 AI 来源

“手动建立关系”不调用模型，需要两份未删除且属于同一可用知识库的知识页；收件箱也可作为共同范围。普通笔记不能作为端点，待审核和已接受知识页均可。

手动新建至少需要一处有效原文引用；界面从两页已有引用中选择依据。引用要能解析到当前资料版本与片段，原话、页码、章节及所属范围仍匹配。冲突类型还必须满足上述双侧证据规则。

来源标记分为 `manual` 与 `ai`。AI 建议被接受后始终保留 `ai`，用户编辑、重新核对、删除或恢复都不会将它变成手动来源。关系保留关联任务和建议 ID，便于区分原建议与之后的编辑。

AI 的同义、相关、前置建议允许没有直接引用，界面会标出缺少原文依据、待核对；接受和保存不代表已验证事实。冲突建议不允许没有双侧依据。直接引用为空也不会取消两页原有引用的版本检查。

## 生成两页关系建议

在“AI 关系建议”中选择另一份知识页、资料范围和可选关注主题，再点击“分析两页关系”。仅用户主动触发，自动整理队列仍只做单份资料分析。

生成前需要满足：

- 两份不同的现有知识页属于同一可用知识库或收件箱；草稿和已接受知识页均可。
- 选择 1—10 份同范围、有可用正文且允许 AI 使用的资料。默认合并两页原有引用涉及的来源，必须保留全部旧来源，可再增加新资料。
- 旧引用仍可访问、版本与原话有效；不能通过取消勾选旧来源绕过检查。选集失效时保留原选择并说明原因，不静默删减。
- 已登录云端账号，当前资料和两页基线已经确认保存，AI 已开启，模型配置、请求账本与次数可用。

两页都没有引用时，也可以选择原始资料进行对照；知识页正文是待分析文本，不能作为证明自身正确的来源。选中的每份资料进入有容量限制的原文上下文，输出只引用实际用于某项建议的依据，不要求每份资料都出现在结果引用中。

单页沿用知识页更新的输入限制：最多 100 个结构块、2 万字符可见正文、6 万字符原始 HTML。除此之外，两份完整页面快照组成的 JSON 数组按 UTF-8 计算，合计不能超过 **120 KiB**；快照包括正文、标题、引用、状态及版本等字段。超限时生成前拒绝，须缩短或拆分页面，不自动截断。

每次返回 0—4 项关系建议，每种类型最多一项，并提供覆盖说明。零项是有效结果，不会强行补足关系。服务端最终结果仍受 **240 KiB** 序列化体积限制；通过 120 KiB 输入预检不保证结果一定能容纳全部建议。

## 审核与维护

结果逐项展示类型、方向、两侧观点与条件、引用和说明。可以接受一项、编辑后接受或忽略一项，其余建议保持待处理。编辑后接受时，引用只能选自该项建议或两页基线原有引用，并再次检查当前有效性。

接受只新增关系及该建议的保存记录，不自动接受知识页、不改写正文；忽略只记录审核选择。已处理的同一建议不能再次建立关系，收起任务也保留已保存关系。

在已建立关系列表中可以编辑类型、两侧观点、条件、说明和引用。保存按当前两页版本重新记录基线，并校验关系自身的 `revision`；若另一操作已修改关系，需要重新打开。重新核对不会清除 AI 来源，也不表示系统认可观点为事实。

删除使用 `deletedAt` 软删除，可从“已删除”列表恢复。恢复保留旧页面快照、证据和来源，仅更新关系自身版本与时间；原本过期的关系恢复后仍显示需要核对。如果已有另一条未删除的同对页面、同类型关系，恢复会被拒绝，避免重复。

## 基线与证据过期

客户端请求只提交当前账号两页的 ID、正文 revision 与更新时间。服务端从该账号已保存的工作区提取完整页面快照，模型不能提供或替换基线正文、版本与引用元数据。

生成前、异步等待后、模型返回及缓存恢复时同时检查两份完整快照和所选资料版本。两页之外的普通笔记编辑不会使本次关系请求失效；账号切换、目标页变化、来源范围或 AI 权限撤回仍会阻止不再有效的生成结果。重新生成绑定原来的两个页面 ID，但重新读取它们当前的版本，不复用旧正文。

审核旧建议时再次检查请求范围、双方完整快照、直接引用及页面原有引用。任一页面正文、标题、引用、状态、所属库、AI 标记或 revision 改变，或页面被删除，旧建议停止应用。把文字改回原样也不会倒退 revision，不能重新激活旧建议。

已保存关系始终保留创建或上次核对时的双页快照。查看时检测页面变化，以及直接引用和两页继承引用的删除、移库、版本或原话变化；失效记录仍可查看，但明确要求重新核对。系统不会用新版本的引用悄悄替换旧证据，删除后恢复也不能绕过这项检查。

关闭 AI 不隐藏已有关系，也不单独阻止人工维护和审核当前有效结果；新生成仍要求完整 AI 权限。恢复被删除页面或来源也不等于旧关系自动有效，仍按当前页面和引用实际状态判断。

## 请求与保存合同

| 对象         | 当前字段及约束                                                                                                                                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 请求         | `OrganizationRequest.kind = "relations"`，`trigger = "manual"`；`targetNote` 与 `compareNote` 均为 `{ id, revision, updatedAt }`，另带 `spaceId`、`sourceIds`、对应 `sourceVersions` 和可选 `topic` |
| 模型结果     | `kind = "relations"`、`mode = "model"`、完整 `target`／`compare` 快照、`relations` 数组与 `coverage`；建议 ID 与类型分别唯一                                                                        |
| 单项建议     | `id`、`type`、`fromClaim`／`toClaim`、`fromCondition`／`toCondition`、`explanation`、`fromCitations`／`toCitations`                                                                                 |
| 已保存关系   | `ConceptRelation` 保存两侧快照 `from`／`to`、上述关系内容、`origin`、`revision`、创建／更新时间和 `deletedAt`；AI 接受记录另保留 `jobId`、`proposalId`                                              |
| 任务审核记录 | `OrganizationJob.savedRelations` 记录建议与关系 ID，`ignoredRelations` 记录忽略的建议 ID                                                                                                            |

服务端通过 `/api/v1/organize` 复用整理请求账本，只让模型提供关系内容和证据编号；真实引用元数据、页面基线与建议 ID 由服务端绑定和校验。账号、串行请求、次数预占、取消、继续原请求及重试规则与 [资料整理](ORGANIZATION.md) 一致。

`WorkspaceData.conceptRelations` 是可选字段，旧工作区无需补齐。完整工作区快照仍保存在 IndexedDB，并通过已有 JSONB 同步。本地第 15 份迁移 `20260914000300_normalized_concept_relations_projection.sql` 已准备 `public.concept_relations` 事务性只读投影，保留双页基线、证据、来源、revision 与软删除状态；连接的 Supabase 项目尚未应用该迁移，浏览器也没有独立关系写入路径。关系检索索引仍未建立。

每个工作区最多 **2000 条关系记录**，包括已软删除的关系。保存前检查最终完整工作区的紧凑 JSON UTF-8 体积不超过 **3 MiB**，关系、双页快照、任务审核记录、资料、笔记和历史共同计入。接受时关系与审核记录一起检查，失败整次拒绝并保留原工作区，不截断内容、不自动删历史。删除不会释放记录数量，也不能作为永久清理方案。

数据库还会按最终 JSONB 文本体积复核，可能比紧凑 JSON 略大；本机预检通过不保证云端保存成功。当前没有关系永久删除界面，达到容量限制后不能继续承诺无限新增。

完整备份 `workspace.json` 保留关系和任务记录。专用导出已包含 `relations.json`、`relation-mapping.json`、每条关系的 Markdown/安全 HTML、双方引用及关系记录时的两页快照；当前页或来源变化会标注状态，不冒充历史版本。具体合同见 [导出格式](EXPORT_FORMAT.md)。

## 验证边界

领域、协调器与服务端测试使用本地数据和模拟返回，覆盖双页范围和版本约束、空建议、证据绑定、AI 来源保持、重复关系、编辑竞态、软删除恢复及容量拒绝等规则。测试通过只能说明这些代码路径符合合同，不能证明模型判断正确、条件充分或引用足以支持结论。

真实模型输出质量、真实 Supabase 双账号与跨设备保存尚待联调。关系图谱可视化属于 M2；本地关系读投影已准备，但关系参与检索、独立写入合同和完整数据清理生命周期仍未实现。当前验收与后续范围以 [开发状态](IMPLEMENTATION_STATUS.md) 和 [PRD](PRD.md) 为准。
