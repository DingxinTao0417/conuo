# Web 原件与遗留本机缓存

当前 Web 使用云端唯一正式存储：工作区在 Supabase PostgreSQL，原件在当前账号的私有 Storage。登录后才能使用；未配置、未登录或初始云端读取失败时，不开启匿名或本机工作区。刷新重新读取云端，不读取旧账号快照、旧同步元数据或本机草稿。完整政策见 [WEB_CLOUD_STORAGE.md](WEB_CLOUD_STORAGE.md)。

## 当前 Web 原件与会话暂存

- 正式阅读和 ZIP 导出从当前账号实时资料取得确切版本，再按权限从私有 Storage 下载原件，普通业务不自动读取 IndexedDB。
- 导入、替换和备份恢复只在页面内存暂存新原件。不可变原件键不能覆盖已有字节，可信 owner 由经过验证的 Auth 身份绑定，不从云端 JSON、ZIP、`blobKey` 或恢复副本名推断权限。
- 协调器复用保存队列，但 `loadLocal`、`saveLocal` 等兼容接口连接的是 `WebSessionStore` 内存适配器，不是第二份持久工作区。内存 CAS 和原子导入保护当前页面的并发操作，云端 revision CAS 保护正式快照。
- 相同账号再次激活保留进行中的暂存，切换账号、退出或应用卸载释放页面快照与字节；旧异步回调不能写入新账号。刷新或关闭不会自动恢复尚未确认的内容。
- “已保存”、恢复成功及知识更新应用成功都等待云端确认。云端未确认时保留当前页面修改供重试或导出，并保护离开与退出；不提供“保留本机草稿并退出”。
- 尚未应用的知识更新审核勾选和编辑仅在当前页面暂存，刷新不恢复。已经接受并保存的正文、历史和审核记录随云端工作区恢复。
- Auth cookie 是登录会话；应用图标、静态资源及用户主动下载的 ZIP 也不构成应用自动维护的本机资料库。本地与云端共存留给未来桌面版，需单独设计与验收。

## 当前 Web 注销保护

已确认的注销响应会停止发起账号的访问和任务，标记该页面会话不可用，再清理它的内存快照、原件和审核暂存。标记不会进入业务工作区、模型请求、ZIP 或浏览器持久存储；普通会话清理和重置不能解除当前页面的注销封锁。刷新后由已验证 Auth 与服务端注销闸门重新检查，不能依靠旧本机标记恢复云端访问。

观察器对已经由 Web 会话管理的账号仅执行内存标记与清理，不自动访问旧 IndexedDB。迟到的账号 A 注销只清理 A，不退出或清理当前账号 B，也不触碰匿名副本。云端 Storage/Auth worker 的完整物理删除与跨设备验收仍待完成。

## 旧匿名资料的主动恢复

旧匿名工作区和原件保留原样。只有用户明确选择“导入旧版资料”时，兼容入口才只读旧匿名快照与可信归属原件，生成 ZIP，经严格校验后作为新副本追加到当前云端账号；非空账号也可导入。缺失或无法证明归属的原件须明确同意只恢复已有文字与引用，不能自动认领字节。

旧账号快照不会在登录或刷新时被恢复成当前工作区；本轮未自动删除旧副本或为另一账号转授原件。重复选择旧副本或同一 ZIP 再次导入会新增副本，不自动去重。同一确认计划失败后的重试则受已有计划身份保护。操作说明见 [BACKUP_RESTORE.md](BACKUP_RESTORE.md)，真实迁移结果以 [CLOUD_E2E_ACCEPTANCE.md](CLOUD_E2E_ACCEPTANCE.md) 为准。

## 历史实现参考

以下章节保留旧 Web IndexedDB 格式、清理协议与当时的测试证据，用于理解遗留数据及未来桌面版评估，**不表示当前 Web 会继续本机与云端共存**。桌面版尚未实现，也不能直接把这些旧测试视为桌面验收。

此前 Web 的原件缓存和工作区快照分别保存在同源 IndexedDB 中。工作区按账号隔离；原件也必须在实际写入字节时记录可信归属，不能仅因云端快照声明了某个 `blobKey` 就允许读取。

## 旧实现：写入和读取

- 新原件以 `{ schemaVersion: 1, blob, ownerIds }` 保存。原子导入在同一交易保存工作区、原件与所属账号；替换、备份恢复和其他本机导入路径同样使用操作开始时的账号。
- 原件键是不可变预留。碰撞不会覆盖已有字节，也不会给后来写入者增加权限。
- 正式阅读器和 ZIP 导出先从当前账号的实时资料记录取得确切版本，再读取该账号有权访问的本机原件；本机缺失时可使用现有受校验的云端 Storage 下载。
- 账号、资料版本或原件记录变化后，旧操作不能把字节交给新上下文。导出使用账号绑定的读取器，不再提前绕过读取器访问全库缓存。
- `ownerIds` 只存在本机缓存内，不进入业务工作区、Supabase JSON、索引或 ZIP；恢复时由当前账号重新写入归属。

当前主 IndexedDB 数据库 `conuo-web` 为 v2，原件值采用上述格式。v1 → v2 保留原有工作区与原件 store，只新增账号注销标记 store；升级不会把未知归属字节授予当前账号。不能把工作区中的后写入引用、资料 ID 或随机缓存键作为归属证明。默认不提供跨登录账号共享缓存的路径。

## 旧实现：匿名资料迁移和清理

用户明确选择把匿名资料迁移至当前登录账号时，仅匿名身份已经有权访问的原件可以增加目标账号的归属；匿名副本继续保留。另一个登录账号的原件不会因这次动作被转授。

删除未提交原件和清理账号缓存也校验归属。清理只撤销当前账号的访问；原件还有匿名或其他可信归属时保留字节。另一份工作区引用原件或记录无法可靠读取时也保留字节，并返回保留计数，不把残留原件说成已物理删除。

## 旧实现：账号注销后的持久封锁

服务器确认注销请求后，协调器先停止该账号的访问、清空内存范围并中止旧任务；在清理主库和独立审核草稿前，将 `{ schemaVersion: 1, accountId, blocked: true }` 持久保存至 `conuo-web` v2 的 `accountDeletions`。标记只包含身份，不进入云端工作区、模型上下文或个人 ZIP。

工作区读取和保存、原子导入、原件读取和预留、清理及匿名原件授权都在自身 IndexedDB 交易中核对标记。账号和其恢复快照已封锁时抛出 `LocalAccountDeletedError`（`LOCAL_ACCOUNT_DELETED`）；没有资料记录也不能重新创建。标记损坏或读取失败时停止访问，不把错误解释为“从未注销”。普通清理重试不会移除标记。

同源标签页通知仅用于提示核对，包含账号与写入者身份，不传正文；接收方必须回读对应账号的持久标记。账号激活、浏览器窗口重新获得焦点及页面返回前台时也会核对。通知通道不可用时，交易内保护仍生效；已经离线的其他设备和另一浏览器存储不受本机通知直接控制。

`pageshow` 同样触发核对，覆盖从浏览器前进／后退缓存返回的页面。搜索、用量、索引、模型状态、结构化问答及截图接口在同源、身份绑定的响应中收到确切 `423 / ACCOUNT_DELETION_PENDING` 时，通过内部观察器同步停止对应账号的访问，再持久封锁与清理；不依赖 BroadcastChannel，没有工作区订阅者也会尝试清理。普通网络失败、401 或其他 423 不构成注销证明。若本机标记无法读取，暂停展示和编辑，保留尚未同步的内部草稿供成功核验后恢复，不据此删除资料。

账号 A 的注销请求已经确认后，晚到的结果仍需清理 A，即使当前已切至 B。清理包括 A 的当前工作区和精确归属的恢复快照，以及实际原件记录声明可信 A 归属的所有字节；失去快照引用的 A 原件也纳入候选。不会通过正文、缓存键相似性或账号 ID 前缀猜测归属。B 的会话不会被退出，B 与匿名副本的字节仍按原保护规则保留。

原件仍有其他可信归属、剩余工作区引用或无法核对的记录时，撤销 A 的访问并保留字节。旧裸 Blob 无法证明归属，继续保守保留。清理计数区分删除和保留，不代表所有浏览器字节已经物理消失。

独立知识更新审核草稿清理失败时，仍尽量完成主库清理；注销标记与访问封锁继续保留，旧草稿回调也被会话代次阻断。界面明确报告尚未完成的清理并允许重试本机清理。主库清理失败时不删除标记，也不能重新开启已注销账号。浏览器数据可能被用户或系统清除，不能保证本机标记永久存在；云端注销闸门仍负责阻止该账号重新访问云端数据。用户已导出的 ZIP 与其他设备副本不能由本机清理撤回。

兼容旧客户端遗留的 `conuo.sync.<accountId>` 本机同步键：它可能包含完整的未同步基线正文，注销时只删除目标账号的精确键，与主库、审核草稿分别尝试并等待结果；失败计入清理失败，不影响其他账号键或站点偏好。Auth 身份事件在服务器验证新身份前同步作废旧弹层操作，事件中的缓存身份不能授权新账号。已经进入 SDK 的 Auth 退出没有取消接口，不能把本机封锁说成能够撤回任意在途退出或阻止旧版本离线客户端的内存展示。

本机封锁不自动应用 Supabase 迁移、不删除其他账号、不启用云端调度或付费资源。真实账号注销、Storage／Auth worker 和跨设备流程须另行完成已授权的云端验收。

## 旧实现：旧版缓存

旧版只保存裸 `Blob`，无法证明所属账号。升级后保留这些字节，不自动读取、授予或删除；也不从现有或后来的云端工作区推断归属。这可能使一部分旧的仅本机原件暂不可读，但资料正文、笔记、引用和历史记录继续保留。

可用的恢复路径：

1. 已有有效的云端原件时，按当前账号权限从 Storage 下载。
2. 重新选择原文件执行明确的“替换版本”，为新版本写入可信原件；旧版记录继续保留，不伪装成旧版本已修复。
3. 恢复先前含原件的 ZIP，创建新资料和版本副本，并为当前账号写入归属。

普通同哈希重复导入可能复用已有资料，不能保证修复旧缓存。不要为了恢复便利，把未知归属原件批量授予当前账号。
